### Crashes

- [x] **App crashes from TestFlight — FIXED & VERIFIED on 1.0.3 (build 7), 2026-07-28.** Confirmed no longer crashing on startup with real menstrual data on TestFlight. Root cause + fix below. Crash logs (from build `1.0.1 (5)`, iOS 26.5.2) show `EXC_CRASH (SIGABRT)` from an Objective-C exception in **`-[NSSortDescriptor encodeWithCoder:]`**, thrown while HealthKit serializes an `HKSampleQuery`'s sort descriptors over **XPC** (`-[_HKSampleQueryConfiguration encodeWithCoder:]` → `NSXPCEncoder`). So it's a **native** crash (the JS error boundary can't catch it), and it fires whenever the app **queries real menstrual data** — which is why Apple's reviewers (empty Health data) never hit it but testers with cycle data crash. `@kingstinct/react-native-healthkit@10.1.0` always attaches `NSSortDescriptor(key: HKSampleSortIdentifierStartDate, …)` (`ios/Helpers.swift` `getSortDescriptors`), and encoding that descriptor over XPC aborts on iOS 26. **Fix (2026-07-28):** patched the library via `patch-package` so `getSortDescriptors` returns `[]` (no sort descriptor sent over XPC). Behavior-neutral: the app already re-sorts samples by date in JS (`packages/domain/cycles/models.ts`) and the query limit (400) never truncates realistic data (~30 samples/180 days), so the returned set is identical. `patches/@kingstinct+react-native-healthkit+10.1.0.patch` + `postinstall: patch-package`. **Requires a new production build (1.0.3) to verify on TestFlight.** _(The error boundary + module-scope background task from earlier still ship as general hardening, but this sort-descriptor patch is the actual crash fix.)_
- [ ] ~~App crashes on launch from TestFlight~~ — original investigation notes (superseded by the diagnosis above, kept for context):
  - **Ruled out:** Supabase config — `client.ts` falls back safely and only `console.warn`s if env is missing (and the prod env vars *are* set on EAS, per the build log). The launch hooks in `App.tsx` (`useCycleSyncLifecycle`, `usePushNotifications`, etc.) all wrap their async work in `.catch`, so a JS throw from them is unlikely.
  - **Leading hypothesis — native crash from the New Architecture + Nitro/HealthKit stack.** `app.config.ts` sets `newArchEnabled: true` (+ `EXPO_USE_NEW_ARCH=1` in `eas.json`), `jsEngine: hermes`, a custom `plugins/withNitroModulesPod` config plugin, and `@kingstinct/react-native-healthkit@10` (Nitro-based). A native incompatibility here would crash before/outside JS and **cannot be caught by a JS error boundary** — it must be read from the crash log. If confirmed, options: verify the Nitro pod setup, pin/upgrade healthkit, or test with New Arch disabled.
  - **Second hypothesis — background task.** `backgroundSync.ts` defined the task only inside `registerCompanionBackgroundSync` (post-mount), violating Expo's rule that `TaskManager.defineTask` run at module scope on every launch; with `startOnBoot`/`!stopOnTerminate`, iOS relaunches the app headlessly to run it, and a missing handler is a known instability source. **Fixed** (2026-07-28): `defineTask` now runs at module load.
  - **Mitigation shipped (2026-07-28):** added an **`ErrorBoundary`** (`app/components/ErrorBoundary.tsx`) wrapping the app, so any *JS* launch error shows a readable screen (with the error text — testers can screenshot it) instead of a white-screen crash. This won't stop a *native* crash but makes JS crashes visible + non-fatal, and is our first diagnostic signal.
  - **DEFINITIVE NEXT STEP — get the crash log** (tells us JS vs native + the exact stack): App Store Connect → TestFlight → the build → **Crashes**; or Xcode → **Window ▸ Organizer ▸ Crashes**; or on the device, Settings → Privacy & Security → **Analytics & Improvements ▸ Analytics Data** (find `Cadence-*.ips`), share it. Also: `eas` device logs via a **development** build reproduces with full JS stacks. _Requires a new production build to test the fixes above (TestFlight runs bundled JS, no OTA configured)._

### Found in a full-codebase review (2026-07-27)

- [~] **Consent is auto-granted on friend-accept — the advertised "explicit mutual consent" isn't what happens (privacy honesty).** 🚧 (WIP — Codex, 2026-07-29) `ensure_friend_sharing` sets `has_shared = true` for **both** directions unconditionally, and it runs on every friend-accept *and* on every `FriendsScreen.loadFriends()`. So the instant two people are friends they can each read the other's cycle snapshot/events — there's no separate opt-in. The "Consent Needed" card in `FriendSyncScreen` is effectively unreachable in the normal flow. This contradicts LEARNINGS.md ("a friend sees your cycle data only if `has_shared=true` on **both** sides… a Consent Needed state until consent is mutual"). RLS itself is sound (non-friends see nothing) — this is a *consent-model / product-honesty* issue, not a leak. Decide the intended model and make code + copy + docs agree. Origin: `supabase/migrations/20251230032000_friend-sharing-helpers.sql`, `friendRequests.respondToFriendRequest`, `FriendsScreen.loadFriends`.
- [~] **No way to revoke cycle-data sharing while staying friends; the toggle is dead code.** 🚧 (WIP — Codex, 2026-07-29) `setFriendSharing(friendId, hasShared)` exists in `friendSharing.ts:44` but is **never called anywhere in the app** — there's no UI to turn sharing off. Even if there were, the next `loadFriends()` would call `ensure_friend_sharing` and force `has_shared` back to `true`, so revocation wouldn't stick. Today the only way to stop sharing is to remove the friend entirely. Pairs with the consent-model bug above.
- [ ] **Duplicate migration files (schema-history hygiene).** ~8 pairs of near-identical migrations exist with underscore-vs-hyphen names, e.g. `20260124162946_event_reactions.sql` + `20260127120000_event-reactions.sql`; also duplicated: `friend_recommendations`, `remove_friend`, `boops_select_events`, `cycle_guidance`, `schedule_cycle_guidance`, `friend_request_email_blind`, `sync_score`. They're idempotent (`create or replace` / `drop policy if exists`), so a fresh DB survives running both — but the history is confusing and error-prone, and it signals the local migration set diverged from what was applied by hand. Reconcile (keep one of each, or document why both exist).
- [x] **Double-tap "like" removes an existing reaction instead of always liking.** Double-tapping a post/event called `handleReaction(target, quickReactions[0])`, and `handleReaction` *toggles* — so double-tapping something you already reacted to with the default emoji **removed** the reaction. _(Fixed: `handlePostPress`/`handleEventPress` now only call `handleReaction` when the default emoji isn't already selected, so double-tap always adds/keeps a like and never un-likes. `HomeScreen.tsx`.)_
- [x] **`loadFeed` is a long serial await-waterfall (perf).** Feed load/refocus runs 8+ dependent `await`s back-to-back (posts → post reactions → post boops → my post boops → events → event reactions → event boops → my event boops → profiles). The independent reads should run with `Promise.all`; today the feed is as slow as the sum of every round-trip, which will feel sluggish on real networks. Origin: `HomeScreen.tsx` `loadFeed`. _(Fixed 2026-07-30: `loadFeed` now runs the posts branch and the cycle-events branch concurrently via `Promise.all`, and within each branch the reactions and boops reads (which only depend on the row ids) run concurrently too. Feed load time drops from the sum of every round-trip to roughly the slowest single chain (fetch → reactions/boops in parallel) per branch. Behavior-neutral: every setState and error path is preserved; only the profiles fetch, which needs both branches' rows, still waits for both. `HomeScreen.tsx`.)_
- [x] **`npm test` is red by default — `architecture-sync.test.ts` hard-fails without `OPENAI_API_KEY`.** The one failure was an LLM-eval test that `throw`s when the key is absent instead of skipping. _(Fixed: the test now uses `it.skip` when there's no key **and** we're not in CI, so `npm test` is green locally by default; in CI it still runs (and fails loudly) if the key is missing. Verified: "1 skipped, exit 0". `__tests__/architecture-sync.test.ts`.)_
- [ ] **Test suite is slow — but the cause is the `jest-expo` cold transform, not the network (diagnosis corrected 2026-07-30).** A full run took ~500s and `npm test` times out in constrained environments, making the "run tests every change" rule painful. **The original theory ("`services/supabase/*` tests hit real Supabase / load `.env`") is wrong:** every one of those tests `jest.mock('../client')`, so they never touch the network — verified by inspection. In fact the **only** genuinely networked/integration test is `__tests__/architecture-sync.test.ts` (an LLM eval needing `OPENAI_API_KEY`), and it *already* `it.skip`s locally when the key is absent. So the cost is almost entirely **`jest-expo`'s Babel/RN transform being recompiled cold for every file** (`preset: 'jest-expo'` in `jest.config.js` applies the full React-Native transform even to pure-logic suites). **Plan (needs a machine where jest actually finishes — it can't be verified in the constrained CLI env, where even a single file times out):** add a second lightweight Jest project/config (`testEnvironment: 'jsdom'` + `babel-preset-expo`, **no** `jest-expo` preset) scoped to the RN/expo-free suites — `packages/domain/**` (models), `app/features/home/utils` (`reactionDoubleTap`), and the mocked `app/services/**` tests (all their target modules were verified to have **no** direct `react-native`/`expo` imports) — and wire it to `npm run test:unit` for a fast inner loop; keep `npm test` (jest-expo) as the full run and put `architecture-sync` behind `npm run test:integration`. Attempted here but backed out: cold `babel-preset-expo` compilation still timed out for every config variant in this environment, so it couldn't be verified — don't merge an unverified `test:unit` config.
- [x] **DST off-by-one in the cycle model (minor).** `buildFlowRuns` split runs with `current - previous > DAY_MS` over local-midnight timestamps, and `dayDiff` divided a local-midnight delta by a fixed 24h — so a 23h/25h daylight-saving day could wrongly split a period run or shift a day count. _(Fixed: added `calendarDaysBetween(from, to) = Math.round((to - from) / DAY_MS)` and use it for `dayDiff`, the run-gap test, and run-length counts. Rounding is correct because DST only shifts ±1h; non-DST cases are unchanged, so all 9 model tests still pass. `packages/domain/cycles/models.ts`.)_
