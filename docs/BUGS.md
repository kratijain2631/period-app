### Crashes

- [x] **App crashes from TestFlight — FIXED & VERIFIED on 1.0.3 (build 7), 2026-07-28.** Confirmed no longer crashing on startup with real menstrual data on TestFlight. Root cause + fix below. Crash logs (from build `1.0.1 (5)`, iOS 26.5.2) show `EXC_CRASH (SIGABRT)` from an Objective-C exception in **`-[NSSortDescriptor encodeWithCoder:]`**, thrown while HealthKit serializes an `HKSampleQuery`'s sort descriptors over **XPC** (`-[_HKSampleQueryConfiguration encodeWithCoder:]` → `NSXPCEncoder`). So it's a **native** crash (the JS error boundary can't catch it), and it fires whenever the app **queries real menstrual data** — which is why Apple's reviewers (empty Health data) never hit it but testers with cycle data crash. `@kingstinct/react-native-healthkit@10.1.0` always attaches `NSSortDescriptor(key: HKSampleSortIdentifierStartDate, …)` (`ios/Helpers.swift` `getSortDescriptors`), and encoding that descriptor over XPC aborts on iOS 26. **Fix (2026-07-28):** patched the library via `patch-package` so `getSortDescriptors` returns `[]` (no sort descriptor sent over XPC). Behavior-neutral: the app already re-sorts samples by date in JS (`packages/domain/cycles/models.ts`) and the query limit (400) never truncates realistic data (~30 samples/180 days), so the returned set is identical. `patches/@kingstinct+react-native-healthkit+10.1.0.patch` + `postinstall: patch-package`. **Requires a new production build (1.0.3) to verify on TestFlight.** _(The error boundary + module-scope background task from earlier still ship as general hardening, but this sort-descriptor patch is the actual crash fix.)_
- [ ] ~~App crashes on launch from TestFlight~~ — original investigation notes (superseded by the diagnosis above, kept for context):
  - **Ruled out:** Supabase config — `client.ts` falls back safely and only `console.warn`s if env is missing (and the prod env vars *are* set on EAS, per the build log). The launch hooks in `App.tsx` (`useCycleSyncLifecycle`, `usePushNotifications`, etc.) all wrap their async work in `.catch`, so a JS throw from them is unlikely.
  - **Leading hypothesis — native crash from the New Architecture + Nitro/HealthKit stack.** `app.config.ts` sets `newArchEnabled: true` (+ `EXPO_USE_NEW_ARCH=1` in `eas.json`), `jsEngine: hermes`, a custom `plugins/withNitroModulesPod` config plugin, and `@kingstinct/react-native-healthkit@10` (Nitro-based). A native incompatibility here would crash before/outside JS and **cannot be caught by a JS error boundary** — it must be read from the crash log. If confirmed, options: verify the Nitro pod setup, pin/upgrade healthkit, or test with New Arch disabled.

This won't stop a *native* crash but makes JS crashes visible + non-fatal, and is our first diagnostic signal.
